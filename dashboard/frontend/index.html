DEMO GUIDE

Recommended live demonstration

This guide uses the real project commands and existing scenario names. Wait times are called out where processing-time or event-time behaviour matters.

  1. Start infrastructure

    Use Start Docker Infrastructure. If Kafka and Flink are already running, the dashboard reports that instead of starting them again.

  2. Submit the Flink job

    Use Submit Flink Job. If a project job is already running, the dashboard avoids submitting a duplicate.

  3. Confirm health

    Check the header pipeline status, the Flink job state and the three dashboard monitor consumers.

  4. Run the normal flow

    Select Normal Flow and choose Generate Once. Open Order States and follow the new order through placed, confirmed, packed, shipped, out for delivery and delivered.

  5. Observe delivery duration

    Select the delivered order. The summary shows the event-time total delivery duration when it is available.

  6. Run duplicate events

    Run Duplicate Events. Look for a DUPLICATE_EVENT record in Exceptions & Alerts. The lifecycle must not advance twice for the duplicate.

  7. Run out-of-order events

    Run Out-of-Order Events. Accepted transitions appear in lifecycle order after event-time processing advances.

  8. Run late events

    Run Late Events. The intentionally late event can appear as EVENT_TOO_LATE while the remaining valid events continue.

  9. Run invalid events

    Run Invalid Events. Look for MALFORMED_EVENT and INVALID_LIFECYCLE_TRANSITION records.

  10. Observe delay alerts

    Delay alerts use processing-time timers and thresholds from config/processing_rules.json. Default thresholds are several minutes, so this step can require waiting or a short test configuration. Do not expect an instant alert.

  11. Inspect checkpoints

    Open Flink & Checkpoints. A completed checkpoint appears after roughly one minute of job runtime. The latest checkpoint ID, timestamp and state size come from the Flink REST API.

Scenario isolation

Finite scenarios use timestamps relative to the current run and add a heartbeat. After one finite scenario, the next finite scenario on the same long-lived job can become EVENT_TOO_LATE. For a clean scenario-by-scenario demonstration, cancel and resubmit the project job before each finite scenario. Continuous mode does not have this limitation.
